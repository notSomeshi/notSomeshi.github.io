能算出来的数,就别写死

有个 bug 在我维护的站点上挂了很久。

图例写着:“红柱为成本最高的三名”。而图上有四根红柱。

没人报错,没人报 bug,构建全绿。因为这两件事——图例里的”三”和标记了 is-costly 的四行 HTML——在代码里根本没有关系。它们只是碰巧在同一个页面上,曾经一致过。

后来加了一行新数据,第四名的成本超过了原来的第三名,而那行 HTML 上的 is-costly 没人记得去掉。

这类 bug 有个共同特征:它不是写错的,是"写对之后放着不管,自己变错的"。
代码没改,数据变了,于是原本正确的描述变成了错误的描述。

这篇讲怎么让这类 bug 从结构上不可能发生。用的是真实案例,代码是真跑在生产上的。

一、第一原则:能算出来的,就别存

看看那张成本图的一行原始 HTML 长什么样:

<div class="rkc-row is-costly">
  <span class="rk-ico b-anthropic">A</span>
  <span class="rkc-name">Claude Fable 5.1</span>
  <div class="rkc-bar"><i style="--w:100.0%"></i></div>
  <span class="rkc-cost">$13,129</span>
  <span class="rkc-task">$7.63</span>
  <span class="rkc-eff">$247.7</span>
  <span class="rkc-score">53</span>
</div>

这里面有七个值。其中只有四个是真数据:名字、总成本 $13,129、每任务成本 $7.63、分数 53。

剩下三个全是算出来的:

值 其实等于
--w:100.0% 总成本 ÷ 最大总成本 × 100
$247.7(每分成本) 总成本 ÷ 分数
is-costly(红柱) 总成本排前三

这三个值被手写在 HTML 里。意味着每次数据一变,人就得重算一遍、改对每一处。而人不会每次都记得。

改成这样之后:

<% rows.forEach(function (r) {
     var cls = (r.star ? ' is-star' : '')
             + (costlySet.indexOf(r.name) !== -1 ? ' is-costly' : '');
%><div class="rkc-row<%= cls %>">
  <span class="rk-ico<%= r.brand ? ' b-' + r.brand : '' %>"><%= r.ico %></span>
  <span class="rkc-name"><%= r.name %></span>
  <div class="rkc-bar"><i style="--w:<%= (r.cost / maxC * 100).toFixed(1) %>%"></i></div>
  <span class="rkc-cost"><%= money(r.cost) %></span>
  <span class="rkc-task"><%= r.task %></span>
  <span class="rkc-eff<%= r.eff < cc.goodThreshold ? ' good' : '' %>">$<%= r.eff %></span>
  <span class="rkc-score"><%= r.score %></span>
</div>
<% }); %>

配一份纯数据:

{
  "goodThreshold": 10,
  "costlyTop": 3,
  "rows": [
    { "name": "Claude Fable 5.1", "brand": "anthropic", "ico": "A",
      "cost": 13129, "task": "$7.63", "eff": 247.7, "score": 53, "star": false }
  ]
}

红柱的判定变成了一行:

var costlySet = rows.slice()
  .sort(function (a, b) { return b.cost - a.cost; })
  .slice(0, cc.costlyTop)
  .map(function (r) { return r.name; });

现在”最贵的三名”这句话和那三根红柱是同一个 costlyTop: 3 算出来的。 它们不可能再各说各话。

判断标准就一句话

这个数能不能从别的数算出来?能,就别存它。

存了派生值,你就是承诺”每次源数据变了,我都会记得同步更新它”。这个承诺你迟早会违约。不是会不会,是什么时候。

二、把”人需要记住的事”往上游推

图表上方有四块统计:

47×        评测总成本极差    $280 → $13,129
17 分      智能指数跨度      36 → 53
37×        每分智能成本极差  $6.7 → $247.7 /分
-59%       并列第一,成本差 2.5 倍

这四块原本也是手写的 HTML。它们比柱长更危险——柱长写错了肉眼能看出来(柱子长度不对),而这几个数字写错了看不出来,它只是一个数字,静静地待在那里撒谎。

全部改成现算:

<%
  var maxC = Math.max.apply(null, rows.map(function (r) { return r.cost; }));
  var minC = Math.min.apply(null, rows.map(function (r) { return r.cost; }));
  var maxS = Math.max.apply(null, rows.map(function (r) { return r.score; }));
  var minS = Math.min.apply(null, rows.map(function (r) { return r.score; }));

  // 并列第一里最便宜与最贵的两家 —— 「同分不同价」那一块
  var top = rows.filter(function (r) { return r.score === maxS; })
                .sort(function (a, b) { return a.cost - b.cost; });
  var cheapTop = top[0], dearTop = top[top.length - 1];
%>
<div class="rkc-stat">
  <b><%= Math.round(maxC / minC) %>×</b>
  <span>评测总成本极差<br><%= money(minC) %> → <%= money(maxC) %></span>
</div>

改完之后的第一次验证很关键:渲染结果必须和原来手写的一模一样。47×、17 分、37×、-59%、2.5 倍——五个数字全部逐字符相同。这说明推导逻辑是对的,不是我换了个算法凑出相近的结果。

然后,今天,这套东西证明了自己值这个钱。

榜单方发布新版本,补测了一批此前没有成绩的模型,其中包括一个 17 分的便宜模型——而在此之前,表里最低分是 36。

第二块统计自己从 「17 分 / 36 → 53」 变成了 「36 分 / 17 → 53」。

我什么都没做。如果它还是手写的 HTML,我几乎肯定会漏掉它——因为我当时满脑子在核对新增那五行的成本数字,不会想到去改图表上方一块看起来跟这次更新无关的统计芯片。

这就是"代码自己维护自己"的真正含义。
不是加个定时任务去跑什么,而是把"需要人记住的事"的数量降下来。人能记住的事情数量是固定的,而项目里需要同步的东西只会越来越多。

三、但不是所有东西都该抽成数据

这一点很容易走过头。

同一个页面上还有一张表,13 个平台 × 7 列。看起来更”表格”,按理说更该抽成 JSON。我没有抽。

因为它的单元格长这样:

<td>
  <strong>Fable 5.1 $10 / $50（新）</strong><br>
  Opus 5 $5 / $25<br>
  <em class="rk-pt-note">💡 <strong>Opus 5 与 Opus 4.8 同为 $5/$25</strong>,
  但 Opus 5 在 AA v4.3.2 下为 <strong>51 分</strong>……
  ✅ <strong>Sonnet 5 的涨价计划已取消</strong>:$2/$10 原为入市促销价,
  <a href="https://platform.claude.com/docs/en/about-claude/pricing">官方定价页已明确转为标准价</a>……</em>
</td>

这不是数据,这是正文。带内链、带强调、带分段。

硬塞进 JSON 会变成什么样?

"apiNote": "💡 <strong>Opus 5 与 Opus 4.8 同为 $5/$25</strong>,但……<a href=\"https://…\">官方定价页</a>……"

要在字符串里转义引号,编辑器不给 HTML 高亮,改一个字 diff 里是一整行变化——比原来更难维护。

那条分界线

抽成数据 留在模板里
结构化:每条记录字段相同 自由文本:每处长短结构都不一样
含派生值:有东西能从别的字段算出来 纯叙述:没有”算错”的可能
会被程序读取、校验、排序 只被人读

那张表两条都不占:它的单元格没有任何派生关系,也没有程序会去计算它。它唯一的问题是长——而长的解法是拆文件,不是换格式。

所以我把它从主模板里切出去,变成一个独立的 partial:

rankings.ejs            626 行  →  117 行
├── _partial/rk-pricing.ejs      248 行
└── _partial/rk-platform.ejs     228 行

改一处文案,现在打开的是 248 行的文件,不是 626 行的。同样降低了维护成本,但用的是完全不同的手段。

⚠ "全部抽成配置"是一种很常见的过度设计。
抽数据的收益来自消除派生值不一致和让程序能校验。如果一块内容两样都不沾,抽出去只是把它换了个更难编辑的地方放着。

四、把检查写成代码,而不是写进文档

派生值解决了”同一个事实的两份拷贝”。但还有一类问题它管不了:两个文件里的两个独立数字,本来应该相等。

比如这个站有两处独立维护的价格:选购助手的方案库里有 priceIn / priceOut,价格对照表里有一份 API 标价。它们写的是同一个事实,但是两套手写数字。

真实后果:有一次 DeepSeek 的按量价在对照表里更新了,在助手里没有——助手用着一个月前的旧价算月账单,把用户的成本算少了一半。页面没报错,没人发现,直到有一次逐条核对才查出来。

这类问题的解法是写成可执行的检查:

// 同一个数可能写成 0.6 或 0.60,两种都认
const forms = n => [...new Set([String(n), n.toFixed(1), n.toFixed(2)])]
  .map(x => x.replace(/[.]/g, '\\.')).join('|');

for (const p of adv.plans.filter(x => x.payg)) {
  const re = new RegExp(`\\$(?:${forms(p.priceIn)})\\s*/\\s*\\$(?:${forms(p.priceOut)})`);
  if (!re.test(pricingHtml)) {
    fail(`助手的 ${p.platform} 标 $${p.priceIn}/$${p.priceOut},价格表里找不到同样的数`);
  }
}

还有一类更隐蔽的:写过的”预告”到期了。

页面上写”促销至 11 月 21 日”——这句话今天是对的,三个月后就是假的。而它比一开始就写错更难发现,因为它当时是对的。

// 到期看板:所有比当前快照新的日期,按剩余天数列出
const today = new Date(snapshot);
for (const [ctx, d] of scanDates(html)) {
  if (d <= snapshot) continue;
  const days = Math.round((new Date(d) - today) / 864e5);
  if (days <= 30) warn(`${d} 还有 ${days} 天 …${ctx}  ← 30 天内,务必重验`);
  else info(`${d} 还有 ${days} 天 …${ctx}`);
}

现在每次构建都会打印:

// 到期看板
     2026-11-12  还有 53 天  …OpenAI 对 Cursor 断供
     2026-11-21  还有 62 天  …官方注明「至少延续到
     2026-12-31  还有 102 天
     2027-01-01  还有 103 天

这些日期原本存在于我的记忆里和一份维护文档里。 记忆会忘,文档不会主动跳出来。现在它们每次构建都自己喊一遍。

五、最重要的一条:沉默不等于通过

写完一套检查,最危险的时刻是它第一次输出”全部通过”。

因为”全部通过”有两种可能:真的没问题,或者你的检查根本没在查。这两种在屏幕上长得一模一样。

所以每加一条规则,我都会故意把数据改坏,确认它真的报错、退出码真的是 1:

# 故障注入:把某一行的 $/分 改成错的
node -e "const f='source/_data/cost-chart.json',d=require('./'+f);
d.rows.find(r=>r.name==='Claude Fable 5.1').eff=200;
require('fs').writeFileSync(f,JSON.stringify(d,null,2))"

node tools/check.js; echo "退出码 $?"
FAIL Claude Fable 5.1 的 $/分 对不上:写的 200,按 cost/score 应为 247.7
退出码 1

好,它是活的。没经过这一步的检查脚本,你不知道它是在保护你,还是只是在每次构建时打印一行绿色的字让你安心。

同理,检查脚本本身也会有 bug。这次就抓到一个:长文案检查一直在误报两条已经收进折叠区的说明——它只认页面上第一个折叠块,后面几个里的内容全被当成”常驻可见文字”。

修完之后我做的第一件事不是提交,而是再注入一条真正超长的常驻文案,确认它还会报错。修误报最容易顺手把真报警也关掉。

六、给 vibe coding 的几条具体建议

让 AI 帮你写代码时,这几件事值得主动说:

1. 明确要求”不要存派生值”。 模型默认会生成看起来最直白的代码——把算好的数字直接写进 HTML。你得明确说”这个百分比按数据算,不要写死”。

2. 把校验规则和功能一起要。 写完一个数据结构,顺手问一句:”这份数据里有哪些字段之间应该满足固定关系?写成检查。” 模型很擅长找出这种关系,但你不问它不会主动写。

3. 重构时要求输出等价证明,而不是”我改好了”。 我这次的验证方式是:把重构后的渲染结果和线上旧版本逐行比对。

天梯 JSON 语义相同: true
总行数 旧 1736 / 新 1736
唯一差异: 一行 is-costly → 普通   ← 就是那个预期的红柱修正

“总行数 1736 = 1736,唯一差异是预期内的那一处” 比任何”已完成”的承诺都有说服力。没有这个,你不知道重构悄悄改坏了什么。

4. 让检查脚本长在仓库里,别长在对话里。 这条我踩过很多次:每次更新都临时写一个一次性脚本,用完就扔,下次重写一遍。现在规则都进了 tools/check.js,npm run build 自动跑。

发现一条新的一致性规则,就加一条进去,下次白拿。

回到开头那个 bug。

修它花了大概十分钟:把 is-costly 从手写改成按成本排序取前三。但真正的收获不是少了一个 bug——是这类 bug 从此不可能再发生。图例里的”三”和红柱的数量,现在是同一个数字。

代码不会自己维护自己。但你可以把它写成一种形状:让”忘记同步”这件事,在结构上没有发生的余地。
